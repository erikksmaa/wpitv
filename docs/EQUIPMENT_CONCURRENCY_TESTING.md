Approval `storage/app/testing/approved.json` harus ditinjau pemilik: identitas lokal tetap, daftar **22 tabel** tepat, tambahan `concurrency_schema_format: "show-create-v1"` dan `concurrency_schema_hash` berisi SHA-256 hasil schema review. Approval lama `schema_hash` tidak ditimpa atau dianggap cocok secara otomatis. File approval tidak dibuat/diperbarui oleh fondasi.
4. Format `show-create-v1`: kumpulkan keluaran `SHOW CREATE TABLE` untuk semua 22 nama yang diizinkan, urutkan key nama tabel, ubah CRLF/CR ke LF, trim kedua ujung DDL, hapus opsi ` AUTO_INCREMENT=<angka>`, lalu hash JSON dengan `JSON_UNESCAPED_SLASHES | JSON_UNESCAPED_UNICODE`. Gunakan `EquipmentConcurrencyGuard::schemaHash()` pada metadata yang telah ditinjau. FK, CHECK, generated column, UNIQUE, charset/collation dan struktur lain tetap masuk hash. Tidak mengubah schema untuk membuat hash cocok.
5. Bootstrap tetap menggunakan `TestEnvironment::initialize/configure`: environment testing, approval identitas, DB berbeda dari `.env`/cached config utama, key testing dan storage/cache terpisah. Base menambahkan pemeriksaan runtime, log null, tanpa koneksi fallback/read-write/socket/URL/prefix, serta PDO nonpersistent. Opsi init-command ditolak. 6. Preflight masa depan membaca `DATABASE()`, `CURRENT_USER()`, `CURRENT_ROLE()`, ID koneksi/server, autocommit, timezone, isolation dan pemeriksaan FK/UNIQUE pada kedua koneksi. Identitas wajib `wpitv_testing` dan `wpitv_test_runner@localhost`, tanpa role MySQL aktif. Kedua PDO/ID koneksi harus berbeda, tetapi server/database sama. Level transaksi Laravel harus nol dan PDO tidak berada dalam transaksi.

Kegagalan setup/cleanup menghasilkan kode `EQCT_*` tanpa kredensial, SQL mentah, payload, atau previous exception. Guard tidak menganggap connection config sebagai bukti identitas server. Jangan menjalankan suite sampai gate tersebut disetujui; opt-in bukan pengganti verifikasi atau izin eksekusi.

## Kontrak fixture dan cleanup untuk fase pengujian berikutnya

- Turunan base membuat fixture hanya dalam `setUpEquipmentFixtures()`, sesudah seluruh preflight lulus. Gunakan run UUID dan case UUID; kategori/kode unit/username memakai prefix `EQCT_<run>_<case>` yang muat batas kolom. Semua nama, nomor mahasiswa, kontak dan catatan adalah nilai sintetis; jangan menyalin data historis.
- Baca ID role existing; jangan update role atau akun existing. Baseline testing aktual ternyata kosong: `EquipmentScenarioTestCase` secara eksplisit membuat hanya empat nama role kanonis sebagai fixture bila belum tersedia, mencatat ID role baru pada ledger, dan menghapus hanya ID tersebut setelah akun fixture dibersihkan. Role yang sudah ada tidak diubah/dihapus. Jangan memakai factory yang dapat `firstOrCreate` role. Setiap category/unit/actor adalah record baru milik kasus itu.
- Buat ledger **sebelum** memulai worker: run/case ID, ID fixture yang berhasil dibuat, token checkout/operasi yang sudah dialokasikan. Simpan journal atomik pada `storage/app/testing/equipment-runs/<run>-<case>.json`, terpisah dari runtime yang dihapus bootstrap. Journal tidak memuat payload peminjam, password, atau kredensial. Parent menggabungkan hasil worker; token memungkinkan penemuan commit yang terjadi sebelum worker mengirim hasil. Prefix hanya pemeriksaan ownership tambahan, bukan klausa delete wildcard.
- Parent meng-commit fixture sebelum worker dibuka. Jangan menjalankan test lain secara paralel pada schema ini. Worker tidak membuat role/master bersama, memakai akun sintetis yang dialokasikan, dan mengembalikan hanya ID/status/kode aman.
- Turunan wajib mengimplementasikan `stopEquipmentWorkers()` dan `cleanUpEquipmentFixtures()`. Base memanggil stop/join terlebih dahulu, rollback transaksi yang tertinggal pada **dua koneksi miliknya**, memeriksa ulang runtime/identitas/grants, baru memanggil cleanup. Transaksi rollback bukan mekanisme penghapusan fixture yang sudah commit.
- Cleanup berikutnya wajib transaksi terpisah dengan DELETE berbatas **ID/token ledger**. Temukan loan yang commit melalui submission token; cocokkan seluruh item dengan unit fixture dan petugas sintetis. Jika ada referensi lintas scope, berhenti dan minta review. Hapus berurutan: audit milik fixture (termasuk export berdasarkan actor fixture), item, loan, unit, kategori, lalu akun sintetis. Jangan menghapus role, baseline, schema, atau histori milik kasus lain; jangan menonaktifkan FK/UNIQUE. Hapus journal hanya setelah commit cleanup dan pemeriksaan tidak ada residu owned IDs/tokens.
- Jika worker mati/timeout atau cleanup gagal, hentikan kasus berikutnya. Pertahankan journal dan lakukan cleanup terarah setelah review dengan identitas yang diverifikasi kembali. Tidak ada sweep berdasarkan prefix, reset database, atau cleanup otomatis saat bootstrap.

## Dua koneksi dan orkestrasi Windows

Base menyediakan `$primary` (`mysql`, default service) dan `$peer` (`equipment_peer`), masing-masing PDO MySQL independen. Transaksi service dapat commit karena tidak ada transaksi luar. Peer dapat dipakai untuk observasi/holding lock; **dua koneksi dalam urutan sinkron belum membuktikan konkurensi**.

Untuk dua service berjalan bersamaan pada Windows/Laragon, fase berikutnya menggunakan dua proses CLI melalui `proc_open` dengan array argv, tanpa shell command concatenation dan tanpa pcntl/dependency baru. Masing-masing bootstrap/memverifikasi environment, grants, schema dan runtime sendiri sebelum melaporkan READY. Kredensial dibaca dari `.env.testing` lokal, tidak dimasukkan argv/stdout/journal. Parent mengirim input sintetis lewat pipe privat; worker memanggil service unchanged pada default `mysql` miliknya. `equipment_peer` dapat menjadi observer; setiap proses memiliki runtime filesystem unik.

Gunakan barrier READY/GO melalui pipe dan deadline bounded, bukan asumsi sleep. Rekam ID koneksi dan hasil commit yang aman. Parent dapat memegang lock target secara eksplisit, melepas dua worker setelah keduanya READY, lalu melepas lock untuk menimbulkan contention. Bukti blocking harus berasal dari handshake/observasi lock yang diizinkan; bila DML-only runner tidak dapat melihat waiter, laporkan batas observabilitas dan ulangi pertukaran urutan pemenang. Jangan menambah privilege global atau mengklaim race teruji hanya dari dua hasil sekuensial. Stop/join seluruh worker sebelum cleanup. Kematian parent/worker dipulihkan menggunakan ledger; worker launcher dan barrier belum diimplementasikan pada fase ini.

## Matriks skenario mendatang

| Skenario | Kontensi dan assertion sesudah seluruh proses selesai |
| --- | --- |
| Checkout unit sama | Dua token berbeda, satu unit/version; tepat satu header/item/receipt commit, satu konflik aman; hanya satu `active_unit_id` dan tidak ada header/audit yatim. Ulangi multiunit beririsan agar seluruh batch kalah rollback. |
| Return parsial | Dua batch sama/beririsan pada header/version sama: satu menang, lainnya stale/tolak seluruh batch. Batch tidak beririsan dengan versi sama tetap berkonflik pada header; retry versi baru dapat menyelesaikan unit sisanya. Unit yang belum kembali tetap terkunci. |
| Loss vs return | Item/header/version sama: tepat satu perubahan sah dan satu receipt. Kehilangan mempertahankan active_unit_id/returned_at NULL dan unit nonaktif. Recovery selanjutnya melalui return, dengan histori hilang tetap ada dan unit tetap nonaktif. |
| Extension vs lifecycle | Dua extension, extension vs return, serta extension vs loss pada header/version sama; cek serialisasi, version, due_at/initial_due_at, unresolved_loss dan due_at_on_return. Keterlambatan sebelum extension tidak hilang dari audit. |
| Retry token | Request identik bersamaan mengembalikan ID transaksi/receipt yang sama, tanpa duplikasi audit. Token sama dengan actor/payload berbeda atau lintas loan harus ditolak. Replay lama tetap valid sesudah master, jatuh tempo atau identitas peminjam berubah. |
| Stale version | Token baru dan versi lama untuk checkout/return/loss/extension/correction/recovery; kode aman dan tidak ada mutasi/audit. Replay token identik diperiksa sebelum stale check sesuai service. |
| Rollback audit | Pada masing-masing proses uji terpisah, pasang listener Eloquent `EquipmentAuditEvent::creating` yang melempar error sintetis tepat sebelum save, lalu lepas listener ketika proses berakhir. Pastikan header/item/unit/version dan receipt tidak berubah/bertambah. Tidak membuat trigger atau mengubah schema; bedakan hasil service rollback dari cleanup. |
| Commit nyata | Observer dengan snapshot baru melihat fixture dan hasil commit pemenang; kedua level transaksi kembali nol. Periksa invariant dan hitungan per ledger, bukan total seluruh database. |
